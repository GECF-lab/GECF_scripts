BRB-seq pipeline — how to run it

A short guide for first-time users: what the analysis does, how to build the STAR index (one-time), how to launch a run, and what the outputs mean.

Contents
1. What is BRB-seq?  ·  2. One-time setup  ·  3. Building the STAR index  ·  4. Running a pool  ·  5. Reading the outputs  ·  6. Common questions

1. What is BRB-seq?

In BRB-seq (barcoded-bulk RNA-seq), cells or samples are loaded into the wells of a 96-well plate. Every well carries a unique 14-base cell barcode (CB) on the oligo-dT adapter. After pooling, all wells are sequenced together, and each read is tagged with the barcode of the well it came from — so the samples are separated in silico instead of in separate sequencing files.

Every pool produces exactly two FASTQ files:

FileLengthContains
R128 ntWell barcode (bases 1–14) + UMI (bases 15–28)
R290 ntThe actual cDNA insert read

The pipeline aligns the cDNA reads with STAR (using STARsolo's CB_UMI_Simple mode) and counts transcripts per well. UMIs let the pipeline collapse PCR duplicates, giving you a molecule-count matrix as well as a raw read-count matrix.

2. One-time setup

  1. Install the conda environment (once per machine): 
    conda env create -f brbseq-env.yaml   # env name: brbseq
    The pipeline finds tools from this environment automatically — you do not need to conda activate before running.
  2. Build the STAR index for your species (one-time, see next section) — or reuse an existing one.
  3. Gather your run inputs: the two FASTQ files of your pool, the lib-prep Excel workbook for the plate (or a barcode TSV), and know which species you sequenced (mouse / human).

3. Building the STAR index one-time

The index is a searchable data structure of your genome + gene annotation; STAR builds it once and reuses it for every subsequent run. It takes a while (hours for a large genome), so build it deliberately.

What you need

  • A reference genome as a FASTA file (.fa or .fa.gz)
  • A gene-annotation file in GTF format (.gtf or .gtf.gz) with chromosome names matching the FASTA
  • (Optional) ERCC spike-in control sequences: both their FASTA and their GTF

The command

conda activate brbseq          # STAR must be on PATH
./build_star_index.sh \
  --fasta /path/to/genome.fa \
  --gtf   /path/to/annotation.gtf \
  --outdir /path/to/STAR_index \
  [--ercc-fasta ercc92.fa --ercc-gtf ercc92.gtf]   # optional pair
  [--threads 8] [--sjdbOverhang 89] [--large-genome]

Options

FlagMandatoryMeaning
--fasta --gtfyesGenome and annotation to index
--outdiryesWhere the index is built (must be empty)
--ercc-fasta + --ercc-gtfoptional pairAdd ERCC spike-in genes to the index (both or neither — one alone is an error)
--threadsoptionalParallelism for the build
--sjdbOverhangoptionalcDNA read length − 1; leave the default 89 for standard BRB-seq 90-nt R2 reads
--large-genomeoptionalExtra RAM limits for very large genomes
ERCC spike-ins need BOTH files. STAR counts reads per gene defined in the GTF. If you add the ERCC sequences (FASTA) but not the ERCC gene records (GTF), your spike-in reads will align fine but count under "unassigned" — silently losing all control values. Both files must use the same contig names, and keeping them in sync is your responsibility.

What a finished index looks like

STAR_index/
├── Genome/                # the searchable genome fragments (the "index")
├── SA                     # suffix-array data structure
├── SAindex                # suffix-array lookup index
├── genomeParameters.txt   # full provenance: exact STAR version, build command,
│                          #   FASTA/GTF used, sjdbOverhang value
├── Log.out                # build log (must say "finished successfully")
├── genome.fa              # the input FASTA, kept alongside for reference
└── annotation.gtf         # the input GTF, kept alongside for reference
                           (plus …_with_ERCC.fa / …_with_ERCC.gtf if the ERCC pair was used)

genomeGenerate produces no Log.final.out — check Log.out for "finished successfully" and confirm Genome, SA, SAindex, and genomeParameters.txt exist. genomeParameters.txt is your audit trail of exactly what the index was built from.

The pipeline also uses the GTF stored in the index directory (at run time) to generate QC inputs, so don't delete the FASTA/GTF copies from a finished index — the dir is a self-contained, shareable blob.

4. Running a pool

The main entry point is brbseq_pipeline.sh. One invocation = one pool.

The script won't run unless utils/ is next to it. brbseq_pipeline.sh finds its helper scripts (barcode parsing, matrix building, BAM demux, QC) in a utils/ folder that must sit in the same directory as the main script, like this: 
BRBseq/
├── brbseq_pipeline.sh      # the main script
└── utils/                  # required — keep in the same folder
    ├── parse_libprep_xlsx.py
    ├── prepare_barcodes.sh
    ├── rename_matrix.py
    ├── prepare_umi_matrix.py
    ├── get_duplication_statistics.py
    └── demultiplex_bam.sh
If you move brbseq_pipeline.sh somewhere else, move utils/ with it (or copy both together) — a missing utils/ is the most common "script just dies" cause and isn't a data problem.

You provide the samples→wells mapping either as the lib-prep workbook (recommended — the parser reads well positions, sample names, and infers the barcode plate from the workbook's own Kit ref row) or as a handmade two-column TSV where the first column is the sample_id and the second is the barcode, separated by one real tab character (i.e. sample_id[tab]barcode, not the word "tab" and not spaces).

Example: workbook mode

./brbseq_pipeline.sh \
  --species mouse \
  --libprep-xlsx /path/to/libprep_phxxx.xlsx \
  --r1 /path/to/Daniel_pool1_S1_R1_001.fastq.gz \
  --r2 /path/to/Daniel_pool1_S1_R2_001.fastq.gz

In workbook mode --run-name is optional — it is inferred from the workbook's Researcher row. No --out-dir needed either — see the output-directory note below.

Example: barcode-TSV mode

./brbseq_pipeline.sh \
  --species human \
  --barcode-tsv /path/to/sample_barcodes.tsv \
  --run-name Daniel_pool1 \
  --r1 /path/to/Daniel_pool1_S1_R1_001.fastq.gz \
  --r2 /path/to/Daniel_pool1_S1_R2_001.fastq.gz

What the TSV file must look like

Exactly two columns separated by one tab character — sample_id and barcode — one sample per line. The header row is optional (the script auto-detects it). The barcode is the 14-base BRB-seq cell barcode from the plate file. Do not write the word "tab" in the file, do not use spaces:

sample_id	barcode
W0_WT_DOX_1	CAGGCAAGGCAACG
W0_SH_DOX_1	CTACCGGAGAATTT
W1_WT_No_DOX_1	AACGCTGCCGTAAT
W3_SH_DOX_2	CTGTATCCTGAGGT
The delimiter must be a real tab character — press the Tab key between the two fields in your text editor. Each line looks like W1_WT_No_DOX_1[tab]AACGCTGCCGTAAT, where [tab] is a single \t character, not the three characters T-A-B and not spaces — spaces will make the file unreadable to the parser. Save it as .txt or .tsv, plain text.
No --out-dir needed — it has a default. On the production server runs land in /mnt/data/BRB-seq_output (each run gets its own timestamped project subfolder: /mnt/data/BRB-seq_output/BRBseq_<run-name>_<timestamp>/, holding the sample-named data folder and the internal QC folder — see section 5). Pass --out-dir <dir> only if you want to send outputs somewhere else.
No --star-genome needed for the usual case. On the production server the STAR indexes for mouse and human already exist, so the script picks the right one automatically from --species. Only pass --star-genome /path/to/STAR_index if you are using a custom index (or a new species).

Even when the pipeline reads the chemistry from the Excel file, the value there can be wrong, so always pass --plate <file> explicitly to guarantee the correct file is used. The plate files (one per chemistry) live in /home/gecf/NGS_pipelines/BRB-seq/BRB_plates — for example --plate /home/gecf/NGS_pipelines/BRB-seq/BRB_plates/barcodes_96_V5A10_brb.txt when your kit is a V5A10 kit, and the matching V5D file for a V5D kit.

What happens inside a run

  1. Manifest — samples, wells, and 14-nt barcodes are joined into a whitelist (empty plate wells included as empty_well_XX rows in workbook mode).
  2. FastQC of both FASTQ files.
  3. STARsolo alignment + counting — one alignment pass that strips the 14-nt CB + 14-nt UMI from read 1, aligns the 90-nt cDNA read, and writes per-barcode gene-count matrices (raw and UMI-deduplicated).
  4. QC & demux — RSeQC read distribution, per-sample BAM demux (picard) and per-sample FASTQ demux (fqtk).
  5. Read-distribution report (FastReadCounter) — runs the same STAR BAM (already on disk, no second alignment) through FastReadCounter with the 96-barcode whitelist, then builds the two legacy-compatible QC reports: files_for_report_and_CLC/<pool>_report_summary.csv (the whole-plate grid — depth / mapped / no-feature / no-alignment per well, in millions, plus an Unknown catch-all) and <pool>_all_stats.csv (raw per-sample totals including all FRC buckets). The jar is a pre-installed production file (see the FRC_JAR line near the FRC step in the pipeline); the gene annotation is taken from the STAR index.
  6. PCA of the UMI matrix (new in v1.3.0, on by default, off with --skip-pca) — runs utils/make_pca.py (script v1.0.0) on the primary result table (the UMI matrix) and writes to files_for_report_and_CLC/PCA_<pool>/. Three orientation PNGs: PC1/PC2 scatter (one dot per well, labelled with the well name, no legend), PC1/PC2 with point size ∝ total UMI, and a per-well elbow plot. Plus well_qc.csv (per-well total_umi + genes_detected). Optional: a missing scanpy or PCA failure only warns — it never blocks the run. Runtime ≈ 4 s (AVT0639, 78k×30).
  7. Final outputs — you take two things into downstream analysis: (a) the sample-named matrix files, and (b) the per-well duplication statistics. The matrix itself exists in two forms of the same data: the raw STAR output where each barcode column is renamed to its Sample_ID (star/samples/), and the ready-to-use CSV tables built from it (matrices/<pool>_umi_matrix.csv for unique-molecule/UMI counts, <pool>_reads_matrix.csv for raw read counts). Use the UMI CSV for PCA/DE; see section 5. The FastReadCounter reports (above) are for sequencing-quality review, not for PCA/DE.
  8. Folder guide + integrity check — the run folder receives a self-generated README.html (an orientation index of everything produced, open in a browser) and, as the very last step, an MD5 manifest <pool>/<pool>.md5 covering every file in the sample folder. Recipient verification: cd <pool>/ && md5sum -c <pool>.md5.

Every step logs to its own file under logs/; the supervisor log (pipeline.log) records each step, its full command line, a pointer to its log, and any failure context. Each step is skipped when its output file already exists, so re-running the pipeline is safe. To pick up an interrupted run, re-run with --resume-dir pointing at the same run folder — the steps that already finished are skipped and the rest continue. If a specific step's output is stale or wrong, delete that step's output file and re-run into the same folder to redo just that step.

How long does a run take?

Measured on a real production pool (run AVT0639: mouse, ~446 M reads, 39 GB STAR-aligned BAM, 30 samples, 32 threads). These are the per-step wall times read from that run's pipeline.log:

StepTime (AVT0639)Notes
Barcode / manifest prep< 1 mininstant — just joins barcodes to wells
FastQC (R1 + R2)~ 25 minscales with read count
STARsolo alignment + UMI counting ~ 30 min the core step — includes building the per-barcode count matrices and the BAM
samtools index< 1 min
RSeQC read-distribution (QC)~ 15 minscales with the BAM size
Duplication stats + matrix renames + UMI/reads CSVs< 1 minall fast matrix reshaping
FastReadCounter report (FRC + two report CSVs)~ 10 minone pass over the BAM with the 96-barcode whitelist; the two report CSVs themselves are instant
PCA of the UMI matrix (v1.3.0)< 1 min≈ 4 s on AVT0639 (78k genes × 30 wells); optional — --skip-pca to turn off; needs scanpy
BAM demux (picard, 30 samples)~ 3.5 hdominant — one picard pass per sample over the whole BAM
FASTQ demux (fqtk, 446 M reads)~ 1–2 minsingle pass, fast (with the run's full thread count)
MD5 manifest (md5sum over the sample folder)~ 5 minestimate — new in v1.2.0, not part of AVT0639's log; the dominant cost is the STAR-aligned BAM
Rule of thumb: expect ~ 4–5 hours end-to-end for a standard pool. About three-fifths of the wall time in AVT0639 (17:11 → 22:02) was the picard BAM demux — every other step combined took about an hour. It is the one step to budget for; it grows with the number of samples, not the read count. Everything else scales with read count.

Times scale with your data: double the reads → FastQC / STAR / RSeQC roughly double; double the samples → BAM demux roughly doubles. Plan on the picard step as the long pole — if you only need the expression matrices you can skip the demux steps entirely (--skip-dmux-bam --skip-dmux-fq) and cut the run to about 1 hour.

5. Reading the outputs

Each run creates a project parent <out-dir>/BRBseq_<run-name>_<timestamp>/ that holds two things: the sample folder (named after the pool — e.g. Lib_01, read out of your FASTQ filenames) with the user-ready data inside, and the internal-QC files_for_report_and_CLC/ folder beside it. When you hand results to a user, ship the whole parent folder — the MD5 manifest inside the sample folder verifies the files they will actually use:

BRBseq_Daniel_pool1_20261023_093000/          project parent (timestamped)
├── Lib_01/                              sample folder (name from your FASTQs)
│   ├── matrices/
│   │   ├── Lib_01_umi_matrix.csv        ★ the table for PCA / DE analysis
│   │   └── Lib_01_reads_matrix.csv      read counts (duplication context only)
│   ├── duplication_statistics.csv       per-well UMI/read ratio
│   ├── star/
│   │   ├── Lib_01_Solo.out/             raw STAR output (sparse matrices, per barcode)
│   │   ├── samples/                     same matrix, columns renamed to sample IDs
│   │   ├── samples_all_wells/           full-plate view incl. empty wells (debugging)
│   │   ├── Lib_01_Aligned.sortedByCoord.out.bam   aligned pool BAM
│   │   └── STAR.log
│   ├── fastqc/                          per-FASTQ reports (.zip / .html)
│   ├── rseqc/                           read distribution + BED12
│   ├── demux_bam/   demux_fastq/        per-sample BAM / FASTQ files

│   ├── README.html                      folder guide (open in a browser)

└── files_for_report_and_CLC/            internal QC — sequencing side, not for users
    ├── Lib_01_report_summary.csv   ★ whole-plate read-distribution grid (depth/mapped/nf/na per well, in millions)
    ├── Lib_01_all_stats.csv        same read-distribution, raw per-sample totals
    └── PCA_Lib_01/                 orientation PCA of the UMI matrix (v1.3.0, optional)

Which matrix do I use?

FileCountsUse for
pool_Daniel_umi_matrix.csv Unique mRNA molecules (PCRs collapsed by UMI, 1-mismatch-tolerant) PCA, Seurat, edgeR, any expression analysis — this is the canonical table
pool_Daniel_reads_matrix.csv All reads, including PCR duplicates Duplication context only. Not for PCA/DE.

Both CSVs have the layout Gene_id, gene_symbol, <sample>… — key downstream analysis on Gene_id (some species references, e.g. mouse, carry a few hundred repeated gene symbols, so the ID is the collision-free key).

duplication_statistics.csv gives the per-well UMI/read ratio — a healthy well typically shows substantial PCR collapse (e.g. ~0.2), while an overloaded or empty well may show a ratio near 1.

Which read-distribution report do I use?

The files_for_report_and_CLC/ folder holds the two FastReadCounter-derived QC tables for the sequencing side:

ColumnMeaning
plate_wellPlate well (A01…H12); NA for samples without a well (e.g. --barcode-tsv mode)
sample_nameYour Sample_ID, empty_well_<WELL> for unoccupied wells, or Unknown for reads with a barcode not in the whitelist
depth_mioTotal reads for that sample (mapped + unassigned), in millions — the whole sample's sequencing footprint
mapped_reads_mioReads assigned to a gene feature (exon model), in millions
no_feature_mioReads that aligned but did not land on any feature, in millions
not_aligned_mioReads that could not be aligned at all, in millions
Use case: PCA / differential expression — use the UMI matrix CSV (above); the report is the sequencing-quality view. A healthy well shows most of depth as mapped_reads; a high not_aligned or very low depth points to a sequencing / library issue rather than a biological result. depth and not_aligned are annotation-independent and reproduce the legacy pipeline's numbers exactly; mapped_reads and no_feature reflect the GTF version the STAR index was built with, so a pool re-run against a newer annotation (e.g. GRCm39.114 → .116) will show a small shift between those two columns only.

6. Common questions

My sample columns are named A01, B04… — where are my sample names?

In workbook mode, sample names come from the workbook's sample-name column and appear in star/samples/ and the final CSVs. If the workbook's name column was missing/empty, the parser fell back to well positions and warned about it — check pipeline.log and re-check the workbook before trusting those columns.

I changed something mid-run / it crashed — do I start over?

No. Re-run the same command with --resume-dir <run>/<pool> (the sample folder inside the run, e.g. BRBseq_Alireza_20261022_171136/Lib_01) and finished steps are skipped. The pipeline decides a step is "done" by looking for its marker file — which is simply that step's own output file (for example barcodes/barcode_whitelist.txt for barcode prep, fastqc/QC_done for FastQC, duplication_statistics.csv for the dups step, or the star/samples/barcodes.tsv rename marker). If a marker + its output exist, the step is skipped; if they're missing or empty, the step re-runs. So to force a single step to redo, delete its marker/output file and resume — the rest still stays skipped.

Can I skip QC steps to save time?

Yes — the QC and demux steps (FastQC, RSeQC, BAM demux, FASTQ demux) are default-on but each is individually skippable via its --skip-* flag. The alignment + matrix chain and the FastReadCounter read-distribution report are mandatory and always run — the report is the QC deliverable, so there is no --skip-frc. The PCA step (v1.3.0) is optional (--skip-pca) — it only warns if scanpy is missing or the step fails, so it never blocks your run.

What if STAR fails with a weird read-count error on 2.7.11b?

Star versions can differ subtly in accepted flags (STAR 2.7.10b and 2.7.11b have known divergences in how they parse some BRB input shapes). Match the pipeline's STAR build to the one your index was built with — the build is recorded in the index's genomeParameters.txt.
